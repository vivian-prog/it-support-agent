# 用一个 VPN 问题理解整个项目

这次使用真实 ChatGPT 模型跑了三轮对话。员工资料、服务状态、手册和用户操作反馈都是模拟的。以下说明根据实际返回和工具记录整理，不是模型内部思考文本。

规划，就是决定接下来先问什么、查什么、查到后做什么。工具调用，就是把“查一下”变成真正执行的查询代码。模型提出下一步，程序执行查询、检查规则并保存记录。

## 第一轮：先把情况问清楚

> 公司的 VPN 每隔十几分钟就断一次，今天上午开始的，已经影响工作了。

实际回答：再告诉我一下，你现在是在家远程办公，还是在公司。

它先记录“VPN 断线，但当前位置未知”，又查了员工资料。资料里写的是办公地点，并不能说明员工此刻在哪里。因此它先追问工作地点，暂时不给具体修复办法。

实际调用：`set_context`（记录已知情况）→ `get_profile`（查员工）→ `finish`（决定追问地点）。

## 第二轮：查资料，选一个可以安全试的方法

> 我在家远程办公，用的是公司配的 Windows 电脑。普通网页能打开，VPN 断了以后内网就用不了。

| 实际工具 | 大白话 | 本次查到的内容 |
|---|---|---|
| get_profile | 查这位员工的设备和权限 | 演示员工使用 Windows 11，有 VPN 权限 |
| check_status | 看 VPN 服务有没有已知故障 | 模拟快照中服务正常，记录未过期 |
| search_kb | 翻公司审核过的排查手册 | 找到切换手机热点、观察 15 分钟的方法 |
| search_history | 看以前类似问题怎样处理 | 有个过去案例在热点下稳定，后来确认与家庭网络有关 |
| check_policy | 看这个方法是否允许执行 | 网络对比检查属于允许的操作 |

从这些查询和回答看，它选的下一步是换个网络做对比。热点下稳定，会增加家庭网络需要进一步排查的可能性；热点下也断，则不能简单把问题归因于家里的 Wi-Fi。历史案例只是提供方向，不证明当前问题原因相同。

实际给出的步骤：

- 先保存手头的工作。如果公司规定和手机套餐允许，可以临时切到手机热点，再连上 VPN。
- 观察 15 分钟，看看还会不会断线，顺便试一下内网能不能打开。不要关闭安全防护，也不用修改安全设置。

## 第三轮：根据试完的结果继续处理

> 我按你说的切了手机热点，也重新连了 VPN，观察了十五分钟，还是会断线，内网也跟着打不开。

这里的“观察了十五分钟”是为了演示而提供的模拟反馈。真实使用时，员工需要实际完成操作再反馈。

它再次记录当前情况、查询员工资料、服务状态、手册、历史案例和操作规则，尝试寻找下一步。最后调用 `finish`，选择 `escalate`，原因是 `unresolved`，也就是试过后仍未恢复。

实际回答：试过之后还没恢复，需要 IT 继续排查。
问题和排查记录已经整理好了，还没发给 IT。你可以下载后交给支持人员。

## 最终交给人工的内容

- 今天上午开始，每隔十几分钟断一次。
- 员工在家办公，使用公司 Windows 电脑，普通网页能打开。
- 断 VPN 后内网不能用。
- 已尝试切手机热点、重新连接并观察十五分钟，仍断线。
- 查过哪些资料、查到的结果、用了哪份操作说明。
- 问题尚未解决，需要人工继续核实。

当前交接记录只保存在本地，可下载，没有真的发给 IT。人工得到这些记录后可以继续查，不用让员工从头重讲。

## 对照代码时只记这几个角色

| 文件 | 可以怎么理解 |
|---|---|
| app/agent.py | 流程负责人：记住情况，调用工具，检查下一步是否允许 |
| app/tools.py | 查询窗口：去演示员工表、服务状态、手册等资料里找结果 |
| app/provider.py | 模型联络员：把对话和工具结果发给模型，接收模型选的下一步 |
| app/store.py | 记录本：保存聊天、排查步骤和结果，下一轮不用重新开始 |

你在面试里可以这样讲：

> 员工说 VPN 老断，我先让系统补齐办公环境，再查员工权限、服务状态和操作手册。资料支持先换热点做隔离检查，程序确认这个操作允许后再给步骤。员工说热点下仍然断，系统就保留试过的方法和失败结果，整理给人工继续排查。

## 本次实际记录

模型：`gpt-6.1-sol`。模型请求 11 次，工具调用 17 次，三轮耗时合计约 65.1 秒，不含真实操作和十五分钟观察时间。

本次第三轮重复查询了员工和手册等信息。可以进一步优化稳定资料的复用，服务状态则按时效重新查询，减少等待和额度消耗。
