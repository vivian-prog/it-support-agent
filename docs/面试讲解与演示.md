# 面试讲解与演示

这份文档帮助你理解和演示项目。请亲自运行、阅读关键代码并做一次自己的修改，再根据真实情况介绍你的贡献。不要把未验证的模型效果、未发生的人工评审或未接通的系统说成已经完成。

## 一分钟介绍

“我选的是员工远程办公时 VPN 频繁断线和内网访问失败。员工往往不知道是本地网络、公司服务还是权限问题，所以系统通过多轮问答收集信息，再查询员工档案、服务状态、知识库和类似案例。

模型负责理解描述、选择查询和提出下一步；代码会验证资料时效、操作权限和运行手册适用条件。提供步骤后仍需员工反馈，确认恢复才关闭。证据不足、服务故障、操作需要审批或排查失败时，生成包含完整上下文的人工接手摘要。

所有后台都是模拟数据。当前本地可直接跑的规则模式用于复现工程行为；真实模型模式支持 API Key 或 ChatGPT 授权。ChatGPT 通道已完成小规模真实模型工具调用评估，具体结果见测试报告。”

## 演示前

1. 在终端进入项目目录，运行 `python3 -m app.server`。
2. 打开 `http://127.0.0.1:8765`。查看顶部模式标签。
3. 展开“演示设置”，选 e001、服务正常，点“开始新会话”。更换选项只有开始新会话后生效。
4. 若演示真实 Agent，先配置模型环境变量，再用 `--mode openai` 启动。演示前跑 `python3 evaluate.py --live`，检查输出和失败案例。
5. 不把规则模式称为模型效果。可把它解释为同一工具和安全边界的可重复基线。

## 演示 A：追问 → 查询 → 验证恢复

依次输入：

> 我的 VPN 每隔15分钟断线。

预期：先问现在是远程还是在办公室。指出系统没有把员工档案的办公室当成当前位置。

> 我在家远程办公。

预期：查询员工、VPN 状态、知识库、历史记录和操作规则；提供热点隔离排查。展开“排查记录”，查看工具返回、状态时间和文章 ID。

讲解：服务正常仅排除了“状态源已经知道的故障”，不能证明一定是家用路由器。历史案例也只能提供假设。15分钟观察是这个排查方法的限制，不能声称已经达成两分钟解决。

> 热点下15分钟没断，内网也能打开了。

预期：用户确认解决。根因仍不能确认为路由器，需要更深入排查才能证实。

## 演示 B：失败后交接

新会话，服务正常，输入：

> 我在家，VPN 显示已连接，但 Grafana 内网打不开。

系统提供经过验证的重连步骤。接着输入：

> 还是不行，已经重新连接了。

规则模式预期：转人工，不重复相同动作。下载 JSON，展示原始问题、尝试、反馈、查询结果、缺失信息和本地交接编号。真实模型可能先补充合理问题；最终不得虚构修复或重复无意义操作。

强调：这里只生成本地交接资料，未发送到 ServiceNow，也没有人工团队实际接单。

## 演示 C：状态工具故障

在“演示设置”选择“服务状态查询失败”，开始新会话：

> 我在家远程，VPN 一直断线。

预期：状态为未知，生成交接，不能说“VPN 服务正常”。可再用过期状态或知识库冲突展示另一种失败。

## 演示 D：权限边界

服务正常，新会话：

> 我刚加入团队，需要开通 Snowflake 生产数据库权限。

预期：查询规则并转人工审批。介绍本系统未提供授权写工具；员工要求紧急处理不会自动扩大系统权限。

## 面试官可能追问

**为什么不用 FAQ？**

这个任务要结合当前用户、服务状态和反馈来决定下一步。FAQ 不维护已经排查的步骤，也不处理带上下文的交接。当前场景很窄，规则基线确实能覆盖；Agent 的价值需要在更多自然表达和新增工具场景下用对比评估证明。

**为什么不做多 Agent 或向量数据库？**

三篇有效文章和少量工具，用单个有边界的编排循环更容易观察和评估。多 Agent 还会增加时延、费用和状态同步复杂度。知识量大后再评估检索方案。

**什么地方由模型决定，什么地方由代码决定？**

模型理解表达、记录用户报告、选工具和提议下一步；代码绑定身份、验证数据和操作、控制预算、渲染审核过的步骤、写入交接。模型不能直接运行任意代码或授权账号。

**为什么不自由生成解决步骤？**

IT 支持里错误的操作建议可能影响安全和可用性。这里选择审核过的步骤和固定问题，代价是灵活性有限。真实上线可以扩充受控操作库，同时评估覆盖率与误转人工率。

**你怎么知道它有效？**

目前有44项单元和集成测试，以及19个确定性场景回归。ChatGPT 授权通道已完成一次真实 VPN 场景试跑：4次模型请求、7次模型选择的工具调用，返回了有资料支持的排查步骤。这仍不代表整体模型准确率、真实根因正确率或用户成功率。API Key 通道保留，尚未用真实密钥实测。

**最明显的局限是什么？**

规则模式表达覆盖有限；成功确认采用保守的短语白名单；数据矛盾检测目前只覆盖不同操作类型的冲突；数据和状态时钟固定；模型目前做的是小规模模拟场景真实调用测试；本地交接未派单；没有 SSO；整机服务锁会限制并发。

**怎么上线？**

先接 SSO 和只读真实工具，验证权限隔离、检索依据和新鲜度；做独立测试集与人工复核；加入监控、时延和费用指标；交接用可重试出站队列并等待工单系统回执。若增加写操作，再设计身份校验、审批和幂等控制。

## 你需要亲自掌握的代码

- `app/agent.py`：从 `turn` 进入，对照 `model_plan`、`finish`、`escalate`。
- `app/tools.py`：五类模拟数据怎么查询；为什么不能指定另一个员工。
- `app/provider.py`：工具 schema、函数调用结果怎样返回模型、为什么必须调用 `finish`。
- `tests/test_agent.py`：模型错误、虚构文章、错误关闭、身份越界怎么验证。
- `evaluation/cases.json`：预期行为有哪些；再自己写几个不同表达的新案例。

建议你真正完成一次小修改，例如补充一个有依据的新运行手册和对应测试，并记录为什么这样设计、验证到了什么。面试时围绕实际做过的工作讲。

## 已接通的 ChatGPT 授权方式

原来的 API Key 接入方式保留。也可以安装 `requirements-chatgpt.txt`，用 `--mode chatgpt` 启动，在 Chrome 或 Safari 从本地应用点击 Continue with ChatGPT 完成授权。账号和模型选择完成后，点“使用这个连接，开始新会话”。这里的 ChatGPT 身份用于模型接入，不代表验证了公司员工身份。

可复制的测试输入：

> 我在家远程办公，用公司 Windows 电脑，VPN 每隔十几分钟就断线，今天上午开始。请查一下我的 VPN 权限、服务状态、相关排查资料和类似案例，再给我一个允许执行的排查方法。

查看模型请求次数，以及标有“模型调用”的排查记录。此输入已经通过一次真实调用验证，具体工具顺序和轮次可能因模型输出变化。开始前选 e001 和“服务正常”，并使用新会话。

## 新增真实模型评估

详见《新增真实模型测试报告-2026-10-22.md》。新增13组口语、英文、多轮和异常输入，首轮11组通过。一处恢复反馈状态被清空的问题已修复；英文例两次发生连接失败，随后真实复测通过。按每组最近一次结果汇总为13/13，但没有在最终代码上重新全量跑13组，不能说成一轮全量通过。

恢复反馈修正后，“现在已经正常了”可以结束当前问题；“还是会断”和“还没试”分别保持升级与等待行为。连接重试只覆盖一次底层传输异常，额度和权限错误不重试，不自动切到 API Key。最后的英文复测没有触发重试，所以不要声称实际网络故障恢复已经经过真实验证。
