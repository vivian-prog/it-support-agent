- 首轮新增真实模型场景：**11/13 通过**。
- 修正上下文问题后的四组针对性复测：**3/4 通过**；英文例子再次遇到连接失败。

## 发现与修正

**恢复反馈被错误当成新问题。** 用户先排查 VPN，再反馈“连续二十分钟没再掉，内网页面也能打开了，现在已经正常了”。原来的关键词分类把“内网”视为新问题，清掉排查记录；同时恢复确认只接受少量固定短语。模型当时已经提出结束会话，程序却重新追问。

修正后，等待 VPN/内网排查反馈时，相关网络描述继续归属当前问题；明确切换话题、权限申请和超出范围请求仍可切换，并清除旧操作依据。恢复确认支持已验证的自然表达，同时拒绝假设、疑问、含混和仍然失败的描述。新增回归覆盖自然恢复、否定反馈、假设及混合失败陈述。真实复测确认恢复可以结束，“根本没解决”仍转人工，“还没试”仍等待。

**英文例子两次发生模型连接失败。** 首轮在资料查询完成后失败，第二次在较早的模型请求处失败。两次都安全转人工，保留了已收集信息；它们没有被计为诊断通过。错误记录不足以确定外部连接失败的根因，因此不将问题归咎于英文理解能力。

加入针对 socket/连接异常的一次有上限重试，并记录重试次数与异常类型。额度、权限、HTTP 拒绝、无效响应不在这项重试内；始终使用同一 ChatGPT 授权，不回退到 API Key 计费。流式响应必须完整结束才执行工具，避免对不完整输出执行操作。重试可能额外消耗订阅额度。最后英文例子的真实复测通过，耗时约 17 秒，但该次没有发生连接重试；恢复机制本身通过模拟超时与连接重置的单元测试验证。

## 检查依据

逐轮保存输入、允许行为、实际行为、响应、调用来源、工具参数与结果、耗时和模型用量；检查不能仅靠出现“转人工”就算通过。工具失败场景要求确实查询到相应失败/过期/冲突证据；任何 `model_error` 都会使该场景的成功路径检查不通过。转人工还检查上下文，切换话题检查旧 VPN 文章未被用作新权限请求的操作依据。报告不包含 ChatGPT 登录凭证或真实账号资料。

`model_calls` 是编排层模型请求数，`transport_retries` 另记。实际模型 HTTP 尝试可能因重试增加；连接失败时无法完整统计对方消耗的 tokens。

## 复现

安装好 ChatGPT 授权依赖、启动本地应用并完成授权后：

```sh
.venv/bin/python evaluate_extended.py --report evaluation/my-extended-run.json
.venv/bin/python evaluate_extended.py --only natural_recovery_confirmation english_paraphrase --report evaluation/my-retest.json
.venv/bin/python -m unittest discover -s tests -v
python3 evaluate.py
```

脚本为每个场景创建独立会话，不使用浏览器里正在进行的会话。运行真实场景会消耗当前选定 ChatGPT 账号的额度。

## 结论范围

这些是同一套模拟后台上的新增口语、英文和异常场景，由助手编写并做了结果复核，不是独立外部测试集。当前结果支持现场演示这些流程；不能据此声称生产准确率、全面安全性或所有陌生问题都能正确处理。模型输出和网络连接仍可能波动，恢复确认仍然采用保守规则，未覆盖的表达可能继续追问。
